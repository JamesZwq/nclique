Graphs model relations between entities, and many graph-mining tasks look for groups of vertices that are densely connected inside~\cite{leskovec2016snap,fortunato2010community,Fang2020Survey}.
%
The $k$-core is the standard answer: the largest subgraph in which every vertex has at least $k$ neighbours~\cite{seidman1983network}.
%
The $(1,s)$-nucleus decomposition of Sariy\"uce et al.~\cite{firstNucleus} keeps the vertex as the unit (the $1$) and counts cliques of $s$ vertices around it instead of neighbours (the $s$).
%
Fix a clique size $s$ and a level $k$.
%
The community of a vertex is the largest connected set containing it in which every vertex lies in at least $k$ cliques of $s$ vertices inside the set.
%
Size $2$ gives the $k$-core, since a clique of two vertices is an edge; size $3$ gives the groups held together by triangles; larger sizes demand denser groups.
%
At every size a vertex has one community per level, and the largest level at which it has one is its \emph{core value} at that size.
%
The size is the parameter that selects the kind of group a query asks for.

\begin{example}\label{ex:intro}
Consider the graph in Figure~\ref{fig:example}.
%
It has a $5$-clique $A=\{a_1,\dots,a_5\}$ and a $4$-clique $B=\{x,b_1,b_2,b_3\}$.
%
It also has a complete bipartite graph between $\{u_1,u_2,u_3\}$ and $\{w_1,w_2,w_3\}$, whose six vertices are all adjacent to $x$; we write $\{u_1,\dots,w_3\}$ for these six.
%
The edge $a_5b_3$ lies in no triangle.
%
At size $2$, the vertex $x$ has $9$ neighbours, and every one of them has at least $4$ neighbours except $b_1$ and $b_2$, which have $3$.
%
The core value of $x$ at size $2$ is $4$, and its community at level $4$ is the seven vertices $\{x,u_1,\dots,w_3\}$, shaded in Figure~\ref{fig:example}(b).
%
$A$ is a second connected $4$-core, cut off once $b_3$ drops out.
%
At size $3$, $x$ lies in $12$ triangles, three inside $B$ and nine of the form $\{x,u_i,w_j\}$.
%
Its core value at size $3$ is $3$, and its community at level $3$ is $N=B\cup\{u_1,\dots,w_3\}$, ten vertices, Figure~\ref{fig:example}(c).
%
$A$ is a separate community, because the edge $a_5b_3$ lies in no triangle.
%
At size $4$, $x$ lies in one $4$-clique, its core value is $1$, and its community at level $1$ is $B$, Figure~\ref{fig:example}(d).
%
The same vertex has a community of $7$, $10$ and $4$ vertices at its own level of sizes $2$, $3$ and $4$.
%
The size selects which group a query asks for.
% trace 2026-09-21: tools/example_check.py; neighbours of x: b1,b2,b3,u1..u3,w1..w3 = 9; triangles of x: C(3,2)+3*3 = 12.
\end{example}

\stitle{Applications.}
The size is the parameter a user changes when the groups of one size are too large or too small.
%
\sstitle{Collaboration networks.}
In a coauthorship graph, where vertices are authors and edges join coauthors, the $k$-core around an author is a broad field~\cite{newman2001structure,ponomariov2016coauthorship}.
%
The communities at larger sizes keep authors who repeatedly write papers with several of the same people.
%
\sstitle{Co-purchase networks.}
In a product graph, an edge joins two products that are bought together~\cite{linden2003amazon}.
%
The community of a jazz album at size $2$ is a core of tens of thousands of products of every kind.
%
At size $3$ it is the albums of the same record company, and at size $5$ the handful of albums a shop would place on the same shelf (Section~\ref{sec:exp}).
%
\sstitle{Coordinated groups.}
Accounts that act together on many of the same targets form cliques, and casual interaction does not~\cite{beutel2013copycatch,hooi2016fraudar}.
%
Larger sizes keep such groups and drop the triangles that arise by chance.

\stitle{Existing methods and their limitation.}
A community query names a vertex $v$, a size $s$ and a level $k$, and asks for the community of $v$ at $(s,k)$.
%
A value query asks only for the core value of $v$ at size $s$.
%
For a fixed size, the communities of all levels are nested, so containment arranges them in a tree.
%
A depth-first traversal of that tree writes the vertices in an order in which every community is one contiguous block of an array~\cite{fastHierarchy,Fang2016CLtree}.
%
Existing indexes for community search store one such tree for one setting: the $k$-core~\cite{Barbieri2015ShellStruct,Fang2016CLtree}, the $k$-truss, which is the same idea over edges~\cite{huang2014truss,akbas2017truss}, or one clique size of the nucleus hierarchy~\cite{fastHierarchy}.
%
Serving every size then means \textbf{\textit{one hierarchy per size}}, which we call \strees.
%
Its limitation is repetition.
%
Call the size of the largest clique containing a vertex its clique number.
%
A vertex lies in cliques of every size from $2$ to its clique number, so it appears in one array per such size and carries one core value per such size.
%
On the web graph \webuk, cliques reach $500$ vertices and a vertex lies in $181$ arrays on average.
%
The index \strees takes $190$~MB for $129{,}632$ vertices, or $1.5$~KB per vertex.
%
On a coauthorship graph with cliques of $337$ vertices it takes $202$~MB for $540{,}486$ vertices.
%
The alternative is to keep no index and to decompose the graph at the queried size when the query arrives.
%
The counting-based decomposition \cnd~\cite{Zhang2026NucleusCounting} needs $15.7$ hours to cover the $499$ sizes of \webuk.

\stitle{Research question.}
This leads to the question this paper answers: \textbf{\textit{how to index the clique-core hierarchies of every size at once, storing each vertex once and returning every community as a few ranges of labels?}}

\stitle{Challenges.}
Within one size the tree of that size answers it.
%
Across sizes it raises three difficulties.
%
\sstitle{Repetition across sizes.}
Within one size, two vertices that lie in the same community at every level are interchangeable and could share one record.
%
However, the communities of a vertex change from size to size.
%
Two vertices that share every community at size $2$ may lie in different communities at size $3$ or $7$.
%
The first difficulty is to decide which vertices can share one record for every size, every level and every query without losing an answer.
%
\sstitle{Contiguity of communities.}
Once vertices are grouped, a community is a set of groups rather than one block of an array.
%
However, the depth-first order of each size lists the groups differently, and a set of group ids is not a few ranges.
%
The second difficulty is to return any community of any size as a few ranges of labels, in constant time.
%
\sstitle{Construction of every size.}
The tree of one size is the output of one decomposition of the graph.
%
However, the sizes are many, cliques reach hundreds of vertices, and one decomposition per size costs hours.
%
The third difficulty is to build the trees of all sizes from one computation.

\stitle{Our idea.}
We start from the queries and ask which pairs of vertices no query can tell apart.
%
\sstitle{Chains.}
Two vertices are \emph{hierarchy-equivalent} when they have the same core value at every size and lie in the same community at every size and level.
%
The \emph{own node} of a vertex at a size is the deepest node of that size's tree containing it, its community at its core value.
%
We prove that two vertices are hierarchy-equivalent exactly when they have the same own node at every size (Theorem~\ref{thm:chains}).
%
The classes of hierarchy-equivalent vertices are therefore read off the per-size trees.
%
We call them \emph{chains}, since a class follows one chain of own nodes through the sizes.
%
Every community is a union of chains, and no partition with fewer classes answers every query (Proposition~\ref{prop:coarsest}).
%
On \dblp there are $13{,}459$ chains for $317{,}080$ vertices, $24$ vertices per chain.
%
\sstitle{Aligned labels, chain order and run arrays.}
We relabel the vertices so that every chain is one interval of labels.
%
A community is then a list of label ranges.
%
We rank the chains by the depth-first positions of their own nodes, size by size.
%
Every size-$2$ community then becomes one range (Theorem~\ref{thm:onerange}), and at larger sizes the same order keeps the ranges few.
%
Each size stores its tree with chains at the nodes, and its depth-first array as maximal runs of consecutive labels with one entry per tree node.
%
After the climb to the queried level, any community is a first range, whole runs and a last range.
%
They are found in constant time (Theorem~\ref{thm:retrieval}) and listed at the speed of a memory copy.
%
Core values are stored per chain and only below the size at which they reach the number of $s$-cliques inside the vertex's largest clique, a binomial coefficient of its clique number.
%
From that size on the value stays at this number (Theorem~\ref{thm:tail}).
%
\sstitle{One clique tree for every size.}
A single clique tree, built once, gives the clique counts of every size.
%
The sizes are processed one after another.
%
Each size reuses the order in which the previous size removed its vertices, whenever a check on clique counts proves the reuse exact (Theorem~\ref{thm:replay}).
%
The tree of each size is built as its core values arrive.

\stitle{Contributions.}
\sstitle{Chains.}
We characterize hierarchy equivalence for $(1,s)$-nucleus decompositions (Theorem~\ref{thm:chains}).
%
Two vertices are told apart by no value or community query at any size if and only if they share their own node at every size.
%
The classes partition the vertices, every community is a union of classes, and no coarser partition answers every query (Proposition~\ref{prop:coarsest}).
%
\sstitle{The chain index.}
We propose \chainidx, an index over chains.
%
Its aligned labels make every chain one interval and map a vertex to its chain in constant time, and its chain order makes every size-$2$ community one label range (Theorem~\ref{thm:onerange}).
%
Its per-size run arrays with one entry per node return any community as the fewest ranges in constant time after the climb (Theorem~\ref{thm:retrieval}).
%
Core values are stored per chain and only below the size at which they reach their closed form (Theorem~\ref{thm:tail}).
%
\sstitle{Construction from one clique tree.}
We build every size from one clique tree.
%
The sizes are processed in turn, each reusing the previous removal order when a check on clique counts proves it exact (Theorem~\ref{thm:replay}).
%
The working memory beyond the clique tree is linear in the vertices and the chains.
%
\sstitle{Experimental evaluation.}
\chainidx is \ratiomin$\times$ to \ratiomax$\times$ smaller than \strees on \numgraphs{} graphs from five families (median \ratiomedian$\times$).
%
It locates a community in \locmin{} to \locmax{}~ns and lists it in \stmin$\times$ to \stmax$\times$ the time of a memory copy of the answer (median \stmedian).
%
It is built for every size \priormin$\times$ to \priormax$\times$ faster than one decomposition per size (median \priormedian$\times$).
%
Two case studies on graphs whose vertices carry names and categories show what the size buys.
%
On DBLP the size that best matches a ground-truth community changes from query to query.
%
On Amazon the size narrows a community from a store to a shelf.
