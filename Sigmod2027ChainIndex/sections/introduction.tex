Graphs model relational data, and many graph-mining tasks seek cohesive groups of vertices rather than single vertices or edges~\cite{leskovec2016snap,fortunato2010community,Fang2020Survey}.
%
The $k$-core is the classical answer: the largest subgraph in which every vertex has at least $k$ neighbours~\cite{seidman1983network}.
%
The $(1,s)$-nucleus decomposition of Sariy\"uce et al.~\cite{firstNucleus} keeps the vertex as the object and replaces the neighbour by a larger witness.
%
Fix a clique size $s$ and a level $k$.
%
The community of a vertex is the largest connected set around it in which every vertex lies in at least $k$ cliques of $s$ vertices.
%
Size $2$ gives the $k$-core, size $3$ the groups held together by triangles, and larger sizes ever denser groups.
%
The size is therefore a knob: the same vertex has one community per size, and the communities shrink as the size grows.

\begin{example}\label{ex:intro}
Consider the graph in Figure~\ref{fig:example}.
%
It has a $5$-clique $A=\{a_1,\dots,a_5\}$, a $4$-clique $B=\{x,b_1,b_2,b_3\}$, and a complete bipartite graph between $\{u_1,u_2,u_3\}$ and $\{w_1,w_2,w_3\}$ whose six vertices are all adjacent to $x$.
%
The edge $a_5b_3$ lies in no triangle.
%
At size $2$, the vertex $x$ has $9$ neighbours; its community at level $4$ is the $4$-core containing it, the seven vertices $\{x,u_1,\dots,w_3\}$.
%
At size $3$, $x$ lies in $12$ triangles, and its community at level $3$ is $N=B\cup\{u_1,\dots,w_3\}$, ten vertices.
%
$A$ is a separate community, because the edge $a_5b_3$ lies in no triangle.
%
At size $4$, $x$ lies in one $4$-clique, and its community is $B$.
%
The same vertex has a community of $7$, $10$ and $4$ vertices at sizes $2$, $3$ and $4$; the size selects which one.
\end{example}

\stitle{Applications.}
The size is the parameter a user tunes when the groups of one size are too coarse or too fine.
%
\sstitle{Collaboration networks.}
In a coauthorship graph, where vertices are authors and edges coauthorship, the $k$-core of an author is a broad field~\cite{newman2001structure,ponomariov2016coauthorship}.
%
The communities at larger sizes keep only authors who repeatedly co-sign papers with several of the same people.
%
\sstitle{Co-purchase networks.}
In a product graph, an edge joins products bought together~\cite{linden2003amazon}.
%
The community of an album at size $2$ is a core of tens of thousands of products; at size $3$ it is the albums of one label, and at size $5$ the handful of albums a shop shelves next to it (Section~\ref{sec:exp}).
%
\sstitle{Coordinated groups.}
Groups of accounts that act together on many targets form cliques that casual interaction does not~\cite{beutel2013copycatch,hooi2016fraudar}.
%
Larger sizes keep the coordinated rings and drop the triangles that happen by chance.

\stitle{Existing methods and their limitation.}
A community query names a vertex $v$, a size $s$ and a level $k$, and asks for the community of $v$ at $(s,k)$.
%
A value query asks only for the core value $\core{s}{v}$, the largest level at which $v$ has a community.
%
For a fixed size, the communities of all levels are nested, and they form a tree.
%
A depth-first order of the vertices then makes every community a contiguous slice of one array~\cite{fastHierarchy,Fang2016CLtree}.
%
Existing indexes for community search store this tree for one parameter: the $k$-core~\cite{Barbieri2015ShellStruct,Fang2016CLtree}, the $k$-truss~\cite{huang2014truss,akbas2017truss}, or one size of the nucleus hierarchy~\cite{fastHierarchy}.
%
Serving every size means \textbf{\textit{one hierarchy per size}}, which we call \strees.
%
A vertex that lies in cliques of $\omg{v}$ vertices then appears in $\omg{v}-1$ arrays and carries $\omg{v}-1$ core values.
%
On the web graph \webuk, cliques reach $500$ vertices and a vertex lies in $181$ arrays on average; \strees takes $190$~MB for $129{,}632$ vertices.
%
On a coauthorship graph with cliques of $337$ vertices it takes $202$~MB for $540{,}486$ vertices.
%
The alternative is to keep no index and to decompose the graph at the queried size when the query arrives.
%
The counting-based decomposition \cnd~\cite{Zhang2026NucleusCounting} needs $15.7$ hours to cover the $499$ sizes of \webuk.

\stitle{Research question.}
This leads to the question this paper answers: \textbf{\textit{how to index every clique-core hierarchy of a graph at once, storing and retrieving each vertex once?}}

\stitle{Challenges.}
Storing each vertex once is easy for one size and hard across sizes, for three reasons.
%
\sstitle{Repetition across sizes.}
Within one size, two vertices of the same community at every level are interchangeable and could share one record.
%
However, across sizes the communities of a vertex change.
%
Two vertices that share every community at size $2$ may part at size $3$ or $7$.
%
Deciding which vertices can share one record for every size, every level and every query, without losing an answer, is the first difficulty.
%
\sstitle{Contiguity of communities.}
Once vertices are grouped, a community is a set of groups rather than a slice of one array.
%
However, each size orders the groups differently, and a list of group ids is not an answer a memory copy can produce.
%
Returning any community of any size as a few ranges of memory, in constant time, is the second difficulty.
%
\sstitle{Construction of every size.}
The hierarchy of one size is built from one decomposition.
%
However, the sizes are many, cliques reach hundreds of vertices, and one decomposition per size costs hours.
%
Building the hierarchies of all sizes from one computation is the third difficulty.

\stitle{Our idea.}
We start from the queries and ask which two vertices no query can tell apart.
%
\sstitle{Chains.}
Two vertices are \emph{hierarchy-equivalent} when they have the same core value at every size and lie in the same community at every size and level.
%
We prove that this holds exactly when the two vertices have the same \emph{own node} at every size (Theorem~\ref{thm:chains}).
%
The own node is the deepest node of that size's tree containing the vertex.
%
The classes, which we call \emph{chains}, are read off the per-size trees.
%
Every community is a union of chains, and no partition with fewer classes answers every query (Proposition~\ref{prop:coarsest}).
%
On \dblp there are $13{,}459$ chains for $317{,}080$ vertices.
%
\sstitle{Aligned labels, chain order and run arrays.}
We relabel the vertices so that every chain is one interval of labels.
%
We rank the chains by the positions of their own nodes across sizes, and every size-$2$ community becomes one interval (Theorem~\ref{thm:onerange}).
%
Each size keeps its tree over chains and its depth-first array as maximal runs of consecutive labels, with one entry per node.
%
Any community is then a head range, whole runs and a tail range, found in constant time (Theorem~\ref{thm:retrieval}).
%
Core values are stored per chain and only below the size at which they reach a closed form (Theorem~\ref{thm:tail}).
%
\sstitle{One clique tree for every size.}
A pivoting clique tree gives the clique counts of every size at once.
%
The sizes are peeled in turn, each reusing the previous elimination order when a certificate on forward counts holds (Theorem~\ref{thm:replay}).
%
Each size's tree over chains is built as its values arrive.

\stitle{Contributions.}
\sstitle{Chains.}
We characterize hierarchy equivalence for $(1,s)$-nucleus decompositions (Theorem~\ref{thm:chains}).
%
Two vertices are indistinguishable by every value and community query at every size if and only if they share their own node at every size.
%
The classes partition the vertices, every community is a union of classes, and the partition is the coarsest that loses no answer (Proposition~\ref{prop:coarsest}).
%
\sstitle{The chain index.}
We propose \chainidx, an index over chains.
%
It has aligned labels with a bitmap map, and a chain order under which every size-$2$ community is one label range (Theorem~\ref{thm:onerange}).
%
Its per-size run arrays with entry points return any community as the fewest ranges in constant time after the climb (Theorem~\ref{thm:retrieval}), and its per-chain values are cut at their certification point (Theorem~\ref{thm:tail}).
%
\sstitle{Construction from one clique tree.}
We build every size from one clique tree, peeling the sizes in turn under a forward-count certificate that reuses the previous elimination order (Theorem~\ref{thm:replay}).
%
The values stream one size at a time, and the working memory beyond the clique tree is linear in the vertices and the chains.
%
\sstitle{Comprehensive experimental evaluation.}
On \numgraphs{} graphs from five families, \chainidx is \ratiomin$\times$ to \ratiomax$\times$ smaller than \strees (median \ratiomedian$\times$).
%
It locates a community in \locmin{} to \locmax{}~ns and lists it within \stmin$\times$ to \stmax$\times$ of a memory copy of the answer (median \stmedian).
%
It is built for every size \priormin$\times$ to \priormax$\times$ faster than one decomposition per size (median \priormedian$\times$).
%
Two case studies on graphs with real semantics show that the best size changes from query to query on DBLP, and that the size zooms from a store to a shelf on Amazon.
