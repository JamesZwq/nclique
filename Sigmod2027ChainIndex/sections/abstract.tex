The $(1,s)$-nucleus decomposition of a graph assigns every vertex a core value for every clique size $s$ and organizes the vertices of each size into a hierarchy of nested communities, the $\Nuc{s}{k}$s.
Answering community queries for every size at once from a stored index has so far meant storing one hierarchy per size, so that a vertex is stored once for every size it participates in.
We show that this repetition is unnecessary.
Two vertices are \emph{hierarchy-equivalent} when they have the same core value at every size and lie in the same community at every level; the equivalence classes, which we call chains, are exactly the vertices that no query can tell apart, and every community is a union of whole chains.
Chains form a partition, so an index over chains stores each vertex once and retrieves each vertex once.
We relabel the vertices so that every chain is one interval of ids, order the chains so that every size-2 community is a single interval, and store each size's hierarchy as a tree over chains whose DFS array is kept as maximal runs of consecutive ids with one entry point per node.
A community is then located in constant time after a jump-pointer climb and reported as the fewest possible id ranges.
Core values are stored per chain and only where a closed form does not apply: once a vertex's value at some size equals the binomial floor given by its largest clique, it equals that floor at every larger size.
On \numgraphs{} graphs from five families the index is \ratiomin$\times$ to \ratiomax$\times$ smaller than one tree per size (median \ratiomedian$\times$), a community is located in tens of nanoseconds, and listing its vertices is at least as fast as copying them.
Correctness is verified against brute force on \selfgraphs{} graphs.
