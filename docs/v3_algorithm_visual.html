AggrCount Convolution (Detailed Example)

Compute AggrCount(τ1, P1) where τ1 = (A,A,B), need jA=2, jB=1:

AggrCount(τ, P) = ∑t f[t] × C(p - t, s - h - t)
where f(x) = ∏c ∈ τ gc(x)
and gc(x) = ∑b C(nhc, jc - b) × C(npc, b) × xb

bc = number of tuple vertices from class c that are pivots on this path.

gA(x) for jA=2
nhA=1, npA=1
bA: max(0, 2-1)=1 to min(2,1)=1
C(1,1)·C(1,1)·x1 = x
×
gB(x) for jB=1
nhB=0, npB=3
bB: max(0, 1-0)=1 to min(1,3)=1
C(0,0)·C(3,1)·x1 = 3x
=
f(x) = gA × gB
x × 3x = 3x²
f[2] = 3
AggrCount = f[2] × C(p-2, s-h-2) = 3 × C(4-2, 4-1-2) = 3 × C(2,1) = 6

support contribution = AggrCount / mult(τ1) = 6 / 3 = 2
Meaning: Path P1 contains 6 (3-clique, 4-clique) pairs for τ1's 3 r-cliques. Each r-clique gets support 2 from this path.

Peeling (Batch Union)

Peel tuples in order of increasing support. All tuples with support = min get core value = min.

Round 1: core = 2

Min support = 2. Tuples τ1, τ2, τ4, τ5 all have support 2.

Peel τ1 = (A,A,B) → core(τ1) = 2

Updating P1 after peeling τ1

τ1 was on P1. On P1, τ1's only feasible allocation was b = (bA=1, bB=1). This becomes a dead box.

Dead box: bA ≥ 1, bB ≥ 1   (requirement: at least 1 pivot from A and 1 from B)

For surviving tuple τ2 = (A,B,B) on P1:

τ2's feasible allocations on P1: (bA, bB) with bA + bB = T = s-h = 3
bA ∈ [0, min(1, npA)] = [0, 1]
bB ∈ [1, min(2, npB)] = [1, 3]

Feasible: (0,3), (1,2)  ← 2 allocations
Dead (bA≥1 AND bB≥1): (1,2)  ← 1 allocation killed

Surviving: (0,3)  → new AggrCount = C(1,1)·C(3,3) · C(0,0) = 1
Old AggrCount was 6. Delta = (6-1)/6 = 0.83
support(τ2) -= 0.83 → 2 - 0.83 = 1.17

For τ3 = (B,B,B) on P1: dead box requires bA≥1 but τ3 has no class A → no effect.

Continue peeling τ2, τ4, τ5 with updated supports...

Round 2: core = 4

Only τ3 = (B,B,B) = {2,3,4} remains. Its support is 4 (possibly reduced by earlier peeling).

core(τ3) = remaining support

Batch Union Problem (the bottleneck)

As more tuples are peeled, each path accumulates more dead boxes. Computing "how many feasible allocations are killed by the union of all dead boxes" is the batch union counting problem:

|⋃i DeadBoxi ∩ FeasibleRegion| = ?

Solved by branch-and-bound: pick a box, partition feasible region, recurse.
Worst case: exponential in #dead boxes.

When ST Wins

ScenarioWhyExample
Sparse graph, low compression Compression ≈ 1x but batch union overhead is huge com-dblp: ST 2-39x faster
Many overlapping cliques Dead boxes accumulate fast → exponential B&B email-Eu-core: ST 157-368x faster
Core issue: V3's peeling trades "fewer peel steps" for "much more expensive per step". On sparse graphs, the compression is minimal (tuples ≈ r-cliques), but the batch union overhead remains. The algorithm needs a fundamentally cheaper peeling update to be competitive everywhere.
