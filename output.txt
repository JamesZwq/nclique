  分析与优化方向

  1. Init 是最大瓶颈（37-42% of total）

  Init 包含两部分：
  - clique Index build：为所有 r-clique 建立 hash 索引
  - countingPerRCliqueParallel：并行计算初始 support

  优化方向：Init 阶段的 clique index build 目前是串行的。可以并行化 hash map 的构建（使用 concurrent hash map 或
  per-thread local maps + merge）。这在 DBLP r=4,s=5 上能省 ~5-6 秒。

  2. Structure 在 YouTube 上占比最高（40-46%）

  YouTube 图的 maxK=17 很小，但 leaf count 很大（3.7M）。这意味着每次 peeling iteration 有大量 leaf 需要 split，tree
  mutation（addNode/removeNode/addNbr/removeNbr）成为主要瓶颈。

  优化方向：
  - Batch tree mutation with pre-allocated IDs：在 Phase B 结束时预计算每个 leaf 产生多少新 leaf，用 atomic fetch-add
  预分配连续 ID 段，然后并行写入 tree.adj_list 和 treeGraphV
  - Pool allocator for DynamicGraph nodes：减少 addNode 中的 vector 内存分配开销

  3. Support 在大 r 时显著增长（r=4 时 占 26-32%）

  r=4 时每个 leaf 的 r-clique 枚举组合数 C(|leaf|, 4) 比 r=3 大得多，导致 Phase B 的 enumerateCombinations 和
  cliqueIndex.byClique() hash lookup 开销飙升。

  优化方向：
  - Phase B 的 hash lookup 优化：byClique() 是瓶颈中的瓶颈。考虑用 perfect hashing 或 SIMD-accelerated hash 替代
  robin_hood hash
  - 减少 incr 枚举：新 leaf 中的 r-clique 如果和旧 leaf 的 r-clique 完全相同（未被删除），其 incr 和 decr
  可以抵消。可以只枚举 "差异" r-clique

  4. YouTube 的加速比最大（6-12x），DBLP 最小（1.5-1.9x）

  原因：DBLP 的 maxK=114（非常深的 core 层次结构），peeling 迭代次数多，每次迭代的工作量小但串行 Phase C
  的占比高。YouTube 的 maxK=17，迭代少但每次工作量大，Phase B 的并行度更高。

  最有前景的下一步：针对 DBLP 类深层次图，优化 Init 阶段的并行化（目前占 37-42%），这是纯并行友好的工作，不涉及 tree
  mutation 的串行约束。

  关键发现

  1. Sparse counting 在 DBLP r=4,s=5 上严重回退

  countingPerRCliqueParallel 从 9.2s 飙升到 20.0s（+117%）。原因是 DBLP r=4 有 16.7M 个 r-clique，而
  robin_hood::unordered_flat_map 的 per-entry 开销远高于 dense array 的直接索引。500K 的阈值让 r=4 走了 sparse path，但
  16.7M entries 的 sparse map 反而比 16 个 dense arrays 更慢。

  修复方向: 将 DENSE_THRESHOLD 提高到远大于 16.7M，或者直接去掉 sparse path — dense path 在所有当前测试 case 上都更快。

  2. Parallel treeGraphV 在 YouTube 上小幅获益

  YouTube r=3,s=4 的 Structure 从 2,186ms 降到 1,928ms（-12%），验证了并行 treeGraphV 更新的可行性。但在 DBLP
  上几乎无变化（6,746→7,002ms），因为 per-iteration 的 leaf 数量较少，并行化的开销超过收益。

  3. V1 Baseline 仍是最佳版本

  在所有 6 个测试 case 中，V1 Baseline（bucket peeling + batch C1/C2）始终表现最好。V3 的两个新优化（sparse counting +
  parallel treeGraphV）都引入了额外开销，在大图上尤为明显。
