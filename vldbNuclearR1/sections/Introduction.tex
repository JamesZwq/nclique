\section{Introduction}\label{sec:intro}

Core decomposition ranks vertices by the amount of cohesive structure that still surrounds them after weak vertices are removed~\cite{kcoreSeidman,coreAlg,communityFinder} and supports a wide range of graph-mining tasks --- community detection~\cite{communities_dec1,communities_dec2,communities_dec3,girvan2002community}, dense-subgraph discovery~\cite{dense_subgraph}, influential-vertex and role analysis~\cite{Identifying_influential,kempe2003maximizing,lu2016vital}, network visualization~\cite{network_visualization}, and applications in social, biological, and security networks~\cite{cohesive_subgraph_Social_Networks,cohesive_subgraph_protein_networks,apply_cyber}.
%
The classical $k$-core uses edges as the witness, but many of these tasks need a stronger witness because a group may pass an edge-degree threshold while containing few triangles, $4$-cliques, or larger coordinated patterns~\cite{ktrussCohen,akbas2017truss,huang2014truss}.
%
The \emph{$(1,s)$-nucleus decomposition}~\cite{nucleusSariyuce14,nuclearTWEB} gives this vertex-centric higher-order ranking: for a fixed $s$, it assigns each vertex the largest value $k$ for which the vertex belongs to a maximal region where every vertex participates in at least $k$ internal $s$-cliques.
%
For $s=2$ it reduces to the $k$-core; for larger $s$ it ranks vertices by progressively tighter clique-supported cohesion.

\begin{example}\label{exa:overview}
Figure~\ref{fig:overview} shows a $10$-vertex graph at $s=3$.
%
The six vertices $v_1,\ldots,v_6$ belong to two triangle-rich $K_4$ blocks; each of them participates in at least three triangles supported by other vertices of the same value, so all six have $(1,3)$-core value $3$.
%
The remaining four vertices $v_7,\ldots,v_{10}$ each lie in one of two pendant triangles ($\{v_6,v_7,v_8\}$ and $\{v_2,v_9,v_{10}\}$), supporting only one triangle each, so all four have $(1,3)$-core value $1$.
%
A formal definition is given in Section~\ref{sec:prelim}; we revisit this graph as a running example throughout the paper.
\end{example}

\stitle{Challenges.}
Computing $(1,s)$-nucleus decomposition at high $s$ is hard because the number of $s$-cliques can be enormous; the current state of the art avoids explicit enumeration with the Clique Path Index, or \cpi{}~\cite{NuclearCD}.
%
Using the \cpi{} efficiently for the vertex-centric case $r=1$ raises four challenges.

\sstitle{Residual state during peeling.}
The general $(r,s)$ algorithm maintains the \cpi{} as mutable residual state, storing per-path vertex sets, a reverse vertex-to-path index, and a priority queue, and rewriting these structures every time a vertex is popped.
%
At $r=1$, peeling removes vertices but never deletes edges, so it is not obvious that the same residual maintenance is necessary.

\sstitle{Memory footprint of the residual index.}
The residual structures dominate memory: per-path vertex hash sets, the reverse vertex-to-path map, and the live Bron--Kerbosch recursion tree together pay constant-factor overhead per vertex--path incidence on top of the clique-encoding cost.
%
A layout whose memory grows with the vertex--path incidence count $\Sig$ alone would let the achievable $s$ on a fixed-memory machine be dictated by $\Sig$ rather than by hash-table overhead.

\sstitle{Construction as the new bottleneck.}
On dense graphs at high $s$, \cpi{} construction takes seconds to minutes per (graph, $s$) configuration and dominates total runtime in any static-index pipeline; parallelising it must avoid the synchronisation cost of mutable path rewrites.

\sstitle{Hierarchy emission from a mutating index.}
The clique-coherent nucleus hierarchy of Definition~\ref{def:nucleus} witnesses $s$-connectivity through $s$-cliques contained in each super-level set, so emitting it requires access to the $s$-cliques themselves.
%
If the \cpi{} is mutated during peeling, those cliques are no longer available afterwards and the hierarchy needs either a second clique-enumeration pass or per-peel-level state, both of which can dominate total cost.

\stitle{State-of-the-Art and Limitations.}
The current state of the art for general $(r,s)$-nucleus decomposition is \cbnd~\cite{NuclearCD}, which maintains the \cpi{} as mutable residual state and inherits four weaknesses when restricted to $r=1$.

\sstitle{Mutable residual-index maintenance.}
\cbnd{} rewrites path records and updates a hash-indexed reverse map at every peel step.
%
These rewrites are a real cost rather than a constant factor: \spinStar{}, which replaces them with closed-form counter updates over a static index, delivers a $17.90\times$ geometric-mean peel-time speedup over \cbnd{} on $451$ matched cells (Section~\ref{sec:exp}).

\sstitle{High memory consumption.}
The residual structures that \cbnd{} must keep mutable in the general $(r,s)$ setting — per-path membership queries, reverse vertex-to-path lookup, and the live recursion tree used to rewrite paths — together cost roughly $88\Sig$ bytes per incidence (Section~\ref{sec:exp}, Table~\ref{tab:mem}), an order of magnitude more than what a static encoding of the same witnesses requires.
%
The geometric-mean memory ratio \cbnd{}/\spinStar{} is $1.55\times$ on the matched cells and $3.92\times$ at maximum; on a billion-scale graph \cbnd{} completes only at $s{=}2$ (using $400$\,GB of $503$\,GB) and exceeds the budget for every $s\ge3$, while \spinStar{} finishes the full $s$ sweep.

\sstitle{Construction as the residual bottleneck.}
Even after cheap peeling, \cbnd{} pays the full construction cost; on \texttt{web-it-2004} (our highest CPI-build-cost benchmark) at $s=3$, construction takes about $137$ seconds and peeling takes about $59$ milliseconds, so the static index builder dominates total runtime by more than $2{,}000\times$ on this configuration.
%
Without a parallel builder, the end-to-end speedup over \cbnd{} stays at $1.05\times$ on the matched cells even though the peel-time speedup is $17.90\times$.

\sstitle{Hierarchy emission re-enumerates or replicates.}
Because \cbnd{} edits the \cpi{} during peeling, its $s$-clique witnesses are gone when the hierarchy is requested.
%
The natural workaround --- the general $(r,s)$ level-DSU hierarchy specialised to $r{=}1$ --- maintains one disjoint-set forest per core level during the peel and exceeds the available $503$ GB on \texttt{wiki-Talk} at $s\!\ge\!9$ where our pipeline finishes (Figure~\ref{fig:hier}); even where it fits, it uses up to $43\times$ more memory (gmean $13\times$ over $24$ matched cells) than emitting the same hierarchy from a preserved \cpi{}.

\stitle{Our Solution and Contributions.}
For $(1,s)$-nucleus decomposition we exploit a static-\cpi{} invariant (Theorem~\ref{thm:vertex-removal}) to deliver a single pipeline that addresses all four challenges above.

\sstitle{Static-\cpi{} invariant for $(1,s)$.}
We prove that vertex peeling never rewrites any \cpi{} path's stored hold or pivot sets (Theorem~\ref{thm:vertex-removal}) and realize the resulting counter-only peel as \spinStar{} (Algorithm~\ref{alg:peelH}), which drops per-incidence space from $\approx 88\Sig$ bytes to $\approx 8\Sig$ bytes (Table~\ref{tab:mem}).
%
On $451$ matched cells, \spinStar{} achieves a $17.90\times$ geometric-mean peel-time speedup and a $1.55\times$ geometric-mean memory reduction over \cbnd{}, and on a billion-scale graph \spinStar{} decomposes the full $s$ sweep while \cbnd{} OOMs for every $s\ge3$.

\sstitle{Parallel \cpi{} construction.}
\paraBuild{} (Algorithm~\ref{alg:parabuild}) parallelises \cpi{} construction across seed vertices, addressing the construction phase that dominates total runtime once peeling is counter-only; empirical scaling reaches $23.4\times$ at $T{=}24$ threads.

\sstitle{Core-value hierarchy from the static \cpi{}.}
\buildHier{} (Algorithm~\ref{alg:buildhier}) emits the $s$-clique-connected super-level join tree from the preserved \cpi{} in $O(\Sig\log\Sig)$ time without re-enumerating any $s$-clique, using up to $43\times$ less memory (gmean $13\times$ over $24$ matched cells) than the level-DSU baseline.

\sstitle{Comprehensive experimental evaluation.}
We compare against \cbnd{} on ten real-world graphs ($451$ matched configurations, headline peel speedup $17.90\times$ gmean / $49.48\times$ max, memory-usage ratio $1.55\times$ gmean), report phase behaviour and parallel construction, push the pipeline to a billion-scale graph (where \cbnd{} only completes at $s{=}2$), and use case studies to evaluate whether the $r=1$ specialization is practically useful.
