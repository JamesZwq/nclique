│ Context                                                                      │
│                                                                              │
│ The pivoter project's nucleus decomposition algorithms consume significant   │
│ memory from shared infrastructure (treeGraphV, edgeGraph, tree) and          │
│ per-algorithm structures (buckets, counting arrays, dual indices). The goal  │
│ is to reduce peak memory without sacrificing runtime performance.            │
│                                                                              │
│ Current memory flow in degeneracy_cliques.cpp:                               │
│ 1. Graph edgeGraph(fpath) — CSR adjacency list (adj_list + adj_list_offsets) │
│ 2. edgeGraph.initCore() — allocates coreV[n] (degeneracy ordering)           │
│ 3. edgeGraph.beSingleEdge() — removes duplicate edges                        │
│ 4. edgeGraph.buildEdgeIdMap() — robin_hood::unordered_flat_map<uint64_t,     │
│ Size> for degree≥1000 + eidToNode[m]                                         │
│ 5. SDCT() → refTree — DynamicGraph<TreeGraphNode> with                       │
│ vector<vector<TreeGraphNode>> adj_list                                       │
│ 6. SDCT_Par7() → par7Result — CliqueCSR<int> (used only for verification,    │
│ NEVER freed)                                                                 │
│ 7. DynamicGraphSet<TreeGraphNode> treeGraphV —                               │
│ vector<robin_hood::unordered_flat_set<TreeGraphNode>>, one set per graph     │
│ vertex                                                                       │
│                                                                              │
│ Per-algorithm additional structures:                                         │
│ - R1 ST: countingV[n], coreV[n], bucket arrays (3 vectors × n), leaf         │
│ metadata (4 vectors × numLeaves)                                             │
│ - R2 ST: countingKE[m], coreE[m], bucket arrays (3 vectors × m),             │
│ leafRmInfo[numLeaves]                                                        │
│ - R3 V4: StaticCliqueIndex (pool_ + mapList_), DualIndex (leafCliqueInfo +   │
│ cliqueLeafIds + counting), bucket arrays (3 vectors × nClique)               │
│ - R3 V11: Same as V4 but LeafCliqueEntry is 32B (adds posMask +              │
│ positions[8]) vs V4's 16B                                                    │
│                                                                              │
│ Key sizes: TreeGraphNode = 8B (63-bit v + 1-bit isPivot bitfield), daf::Size │
│  = uint32_t = 4B.                                                            │
│                                                                              │

  1. R3 V11 收益最大：peak memory 降低 11-17%，来自 freeMapList() (Opt 4) +

  coreV 释放 (Opt 2) + eidToNode 释放 (Opt 3)
  4. R2 ST 收益较小：降低 2-4%，因为 R2 需要保留 eidToNode，只受益于 Opt 1+2
  5. 运行时间无回退：所有配置 ±3% 以内，属于正常波动
  6. 与 Reference 对比：R1/R2 ST 优化后内存已经 低于 Reference（com-dblp 上 R1
  ST 比 Reference 少 39%，R2 ST 少 44%）；R3 V4/V11 仍高于
  Reference（因为需要额外的 clique index + dual index），但差距已缩小

  理论创新要点

  核心创新：Immutable-Tree Counter-Based Peeling

  传统方法在 peeling 过程中 物理修改 Clique Tree — 每个 peeling step
  都要删除叶节点、移除 pivot、重建 treeGraphV。这导致:
  - 每一步都有 O(|leaf|) 的树变异开销
  - treeGraphV 的 hash set 操作 (insert/erase) 成本高
  - 堆 update 是 O(log n) per affected vertex

  ST 的核心观察是：对于 r=1，支持度变化完全由叶节点的 pivot 
  减少量决定，可以用闭合数学公式 nCr[old] - nCr[new] 
  一次性算出，无需遍历叶内成员。 因此 tree 和 treeGraphV 可以保持
  immutable，整个 peeling 过程只操作整数计数器。

  这将 每叶 peeling 开销从 O(|leaf| × log n) 降为 O(|leaf|)（bucket vs
  heap），并消除了所有树变异的常数因子。

  合并成一趟：遇到叶时立即判断 case 并处理 delta + 树变异，减少 removedLeaf

  理论创新要点

  核心创新 1: Clique-Leaf Dual Index (V4)

  传统 (r,s)-nucleus decomposition 在每个 peeling step 需要:
  1. 用 intersect_dense_sets_multi 做 r 路 hash set 交集 找受影响的叶 —
  O(|smallest_set| × r × hash_probe)
  2. 对每个受影响叶 重新枚举 C(n,r) 个 r-clique 并用 byClique() hash 查找 —
  O(C(n,r) × hash_probe)

  Dual Index 的创新是：在 init 阶段一次性构建 clique→leaf 和 leaf→clique
  的双向映射。这将 Phase 1 从 O(r × hash) 降为 O(1) array lookup，Phase 2 从
  O(C(n,r) × hash) 降为 O(|entries|) sequential scan。

  这是最大的理论贡献：它证明了 (r,s)-nucleus decomposition 的 peeling 过程可以在
   不做任何 hash 查找 的情况下完成 support 更新，只需要预计算的数组索引。

  核心创新 2: Bitmask-Containment BK Propagation (V11)

  当 BK 拆分生成子叶时，传统方法对每个子叶重新枚举 C(n',r) 并做 hash 查找。V11
  的创新是：

  1. 在 LeafCliqueEntry 中存储 r-clique 的 叶内位置 (positions)
  2. BK 的输出是一个 bitmask (childMask) 表示哪些位置保留
  3. Containment test 变为 (posMask & childMask) == posMask — 一条 AND + 一条
  CMP
  4. Pivot count 变为 popcnt(posMask & pivotMask) — 一条 AND + 一条 POPCNT

  这将 BK case 中每个 r-clique entry 的判断从 O(r × hash probe) 降为 O(1) 
  bitwise operation。

  1. Immutable-Tree Counter Peeling (R=1): 我们证明了对于 r=1 的 vertex-level
  nucleus decomposition，SDCT 上的 peeling
  过程可以完全避免树变异——只需对每个叶维护两个整数计数器，support delta 通过 nCr

  替代），将 peeling 的 每步复杂度从 O(|leaf| × log n) 降为 O(|leaf|)。

  阶段一次性构建的双向映射：(clique → containing_leaves) 和 (leaf →

  降为 O(1) array indexing

  scan
    - 这是 渐近改进，不仅是常数因子优化
  3. Bitmask-Containment BK Propagation: 在 BK
  拆分的子叶重建中，利用预存储的位置索引实现 O(1) bitmask containment
  test，替代传统的 O(r) per-entry membership test + hash rebuild。
