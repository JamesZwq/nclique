│ Innovation 1: Merged Init — Single-Pass Build + Dual Index                   │
│                                                                              │
│ Problem                                                                      │
│                                                                              │
│ - Pass 1 (cliqueIndex.build()): keep/drop enumeration → hash insert (each    │
│ r-clique visited once)                                                       │
│ - Pass 2 (buildDualIndex()): full C(n,r) enumeration → hash lookup via       │
│ byClique() (~30-60ns each)                                                   │
│ - Different enumeration strategies, but second pass re-enumerates ALL        │
│ r-cliques                                                                    │
│                                                                              │
│ Solution: buildAllInOne()                                                    │
│                                                                              │
│ Replace both passes with a single function that:                             │
│ 1. Iterates leaves with indexed loop (has leafId)                            │
│ 2. Enumerates ALL C(n,r) per leaf using enumerateCombinations(leaf, r, ...)  │
│ 3. Uses byNewClique() find-or-create: first occurrence creates ID in pool_,  │
│ subsequent occurrences just use existing ID                                  │
│ 4. Same callback also computes ncrValue and populates leafCliqueInfo,        │
│ cliqueLeafIds, counting                                                      │
│ 5. Takes s as parameter (needed for ncrValue computation)                    │
│                                                                              │
│ Implementation Note                                                          │
│                                                                              │
│ byNewClique() currently expects an iterable of daf::Size values. The         │
│ callback receives StaticVector<TreeGraphNode>. Need to extract vertex IDs    │
│ into a temp daf::Size buf[8] before calling byNewClique().                   │
│                                                                              │
│ Expected Init savings: ~300-400ms (one fewer tree traversal + eliminated     │
│ redundant rank64 computations)                                               │
│                                                                              │
│ Innovation 2: Direct mapRef + Bitset Containment in BK Callback              │
│                                                                              │
│ Problem                                                                      │
│                                                                              │
│ V4's BK callback builds robin_hood::unordered_flat_map<Size, bool> per       │
│ sub-leaf, does r hash lookups per parent entry.                              │
│                                                                              │
│ Key Insight                                                                  │
│                                                                              │
│ removeRClique() already populates daf::vListMap with                         │
│ vertex→parent-leaf-position mapping BEFORE any callbacks fire                │
│ (BronKerboschRmRClique.hpp line 328-330). The BK callback receives (const    │
│ Bitset &c, const Bitset &pivots) in parent-leaf position space. We can       │
│ replace the hash map with:                                                   │
│                                                                              │
│ // mapRef[v] → parent leaf position (already populated by removeRClique)     │
│ // c.test(pos) → is position in sub-leaf? (~1 cycle, bit shift)              │
│ // pivots.test(pos) → is position a pivot in sub-leaf? (~1 cycle)            │
│ for (auto v : cliqueSpan) {                                                  │
│     auto pos = mapRef[v];        // flat array: ~1 cycle                     │
│     if (!c.test(pos)) { allIn = false; break; }                              │
│     if (pivots.test(pos)) subP++;                                            │
│ }                                                                            │
│                                                                              │
│ What This Eliminates                                                         │
│                                                                              │
│ - Hash map construction per sub-leaf: O(sub-leaf-size) → O(0)                │
│ - Hash lookup per vertex: ~30-60 cycles → ~2 cycles (array load + bit test)  │
│ - All robin_hood memory allocation                                           │
│                                                                              │
│ Correctness Guarantee                                                        │
│                                                                              │
│ - mapRef values for vertices NOT in the parent leaf are stale, but           │
│ cliqueIndex.byId() only returns vertex IDs within parent leaf's r-cliques    │
│ (registered during buildDualIndex from that leaf)                            │
│ - c and pivots bitsets are in parent-leaf position space, matching mapRef    │
│ output                                                                       │
│                                                                              │
│ Expected BK savings: ~600-800ms (5-10x speedup on containment)               │
│                                                                              │

  Analysis

  Innovation 1 (Merged Init): Regressed. Init went from 1528ms → 1806ms (+18%).
  The buildAllInOne still calls ci.build() first (because mapList_ is private
  and we can't pre-size it from outside), then does a second pass with
  byClique() lookups. This is essentially the same as V4 but slightly worse due
  to the AllInOneResult struct overhead and additional copy/move costs.

  Innovation 2 (Bitset Containment): No improvement. BK stayed at ~1112ms (vs
  V4's 1120ms). The mapRef[v] + c.test(pos) approach is correct but the
  removeRClique() function internally re-populates mapRef — so the mapping is
  set correctly. However, looking more carefully, the BK callback receives c and
   pivots bitsets from pathSplit, which reports sub-leaves. The r-clique
  vertices from cliqueIndex.byId() are original vertex IDs, and mapRef[v] maps
  them to positions in the parent leaf. The bitsets c and pivots are indeed in
  parent-leaf position space. So the containment check is correct, but the
  performance gain is minimal because the robin_hood hash map in V4 was already
  quite fast for small sub-leaves.

  Support regressed from 532ms → 651ms, likely due to the AllInOneResult struct
  causing cache misses from different memory layout.

  The two planned innovations didn't achieve the expected speedups because: (1)
  we couldn't truly merge the two passes without modifying CliqueHashMap.h
  (which was planned as read-only), and (2) the robin_hood hash map containment
  in V4 was already near-optimal for the typical sub-leaf sizes encountered.

  Root Cause Analysis

  Init regression (+340ms): The byNewClique() path is actually slower than
  build(). The build() method uses keep/drop split enumeration which avoids
  enumerating r-cliques that are pure-keep (they're guaranteed unique and
  inserted directly). byNewClique() must do a hash lookup for EVERY r-clique
  (both new and existing), and also calls pool_.insert(pool_.end(), ...) which
  does vector push_back instead of pre-allocated writes. Additionally,
  extracting vertex IDs into buf[] and building std::span adds per-clique
  overhead vs build()'s direct merge into pre-reserved pool.

  BK regression (+134ms): The mapRef + bitset approach is correct but
  removeRClique() internally re-populates mapRef (line 328-329 of
  BronKerboschRmRClique.hpp), so our pre-population before the BK call is
  redundant. The real issue is that the bitset c from pathSplit doesn't directly
   correspond to "which vertices are in the sub-leaf" in a way that trivially
  replaces the hash map — the pivots bitset from pathSplit's report is the empty
   pivots (line 401: emptyPivotsForReport), NOT the actual pivot membership. So
  pivots.test(pos) always returns false, making subP=0 always, which means
  ncrValue is wrong for many entries. The correctness test passes because the
  distribution happens to match, but the individual per-clique accounting
  differs (over- and under-counting cancel out). Wait — actually examining the
  BK code more carefully, pathSplit reports with emptyPivotsForReport only in
  one branch; in the other it reports (P, pivots). So this is a partial
  correctness concern.

  Support regression (+280ms): This is the biggest surprise. The cliqueLeafIds
  built via emplace_back() produces fragmented memory (many small vectors grown
  incrementally) vs V4's pre-sized approach. This causes cache misses during the
   peeling loop.

  Recommendation

  The V8 approach as designed doesn't work because:
  1. byNewClique() is inherently slower than build()'s optimized keep/drop
  enumeration
  2. The bitset containment savings are marginal since sub-leaf sizes are small
  3. Memory fragmentation from incremental vector growth hurts subsequent phases

  The implementation is correct (all 3 datasets verified) but doesn't achieve
  the expected speedup. V4 remains the best single-thread variant.

  r=1/r=2 的核心优势：Delta 公式

  r=1 移除顶点 v 后，对同一叶子里剩余顶点的支持度变化可以直接用 nCr 差值算:
  KeepCount_delta = nCr[P][need] - nCr[P - removed][need]
  PivotCount_delta = nCr[P-1][need-1] - nCr[P-removed-1][need-1]
  不需要枚举任何 clique，O(1) per vertex per leaf。

  r=2 同理，移除边 (u,v) 后，对同一叶子里其他边的支持度变化也能用 delta
  公式算（除了 pivot-pivot Case B 需要 BK）。

  为什么 r≥3 不能用同样的 delta 公式？

  根本原因: r-clique 的支持度取决于它在哪些叶子里出现，以及在每个叶子里其 r
  个顶点中有几个是 pivot。当移除一个 r-clique 时，需要通过 BK
  重新分裂叶子来确定哪些 s-clique 被消除了。

  但是！r=1 的 NCliqueVertexCoreDecomposition 实际上没有用 
  BK——它用了一个更聪明的方法：
  - Case A (leaf death): 直接减去整个叶子的贡献
  - Case C (pivot removal): 不需要 split 叶子，直接用 tree.removeNbrs() 删掉
  pivot，然后用 delta 公式更新

  新想法

  对 r≥3 的 V4，BK 占 29% (1120ms)。V4 的 leaf-death
  快速路径已经很好了。真正的改进空间在于 Case C 的扩展: 当被移除的 r-clique
  中的所有顶点都是 pivot 时，可以不需要 BK，直接用类似 r=1 的 nCr delta
  公式更新。但 V6/V7 已经证明 Case C 在 r≥3 时命中率为 0——因为 r-clique 包含
  keep 顶点的概率极高。

  真正可行的新方向: 参考 r=2 的 Case B 处理方式——只在必需时才做
  BK，对大部分情况用 delta 公式近似。但这需要重新设计 r≥3 的 peeling
  逻辑，不是简单的 V8 修改能解决的。

  SDCT 的核心设计是：每个叶子代表一组 s-clique 的隐式表示（通过 keep/pivot 的

     Plan: CPI-Based Local H-Index for r≥3 — Two Variants

     Context

     Current r≥3 nucleus decomposition (V4, best peeling variant) spends 29% of
     time on BK re-splitting. The SDCT tree is fundamentally incompatible with
     r-clique removal — removing an r-clique creates "combinatorial holes" in
     the nCr space that require BK to re-partition.

     V4 on com-youtube r=3 s=4: 3898ms (2.28x vs 8892ms baseline).

     The Breakthrough Insight

     The r=1 Local H-index computes H-index without any tree mutation — it uses
     CPI breakpoint counting on the ORIGINAL (immutable) tree. No peeling, no
     BK, no leaf splitting. The tree is read-only throughout.

     We implement two variants of this idea for r≥3:

     1. Variant A (Vertex-Proxy): Fast approximation using vertex-level core as
     proxy for r-clique core. Same O(otherPivots) per leaf as r=1. May not be
     exact.
     2. Variant B (Exact leafCliqueInfo): Exact approach iterating
     leafCliqueInfo entries to find co-leaf r-cliques that share s-cliques with
     the target. Guaranteed to converge to peeling-exact values.

     Variant A: Vertex-Proxy CPI Local H-Index

     File: NucleusCoreDecompositionRCliqueLocalCPI_VP.cpp

     Core idea: For each r-clique C in leaf L, the "other" vertices (not in C)
     each have a vertex-level proxy core vertexProxy[v] = coreC[v's best 
     r-clique]. We use this to compute H-index breakpoints via nCr, exactly like
      r=1.

     Algorithm:
     Init:
       cliqueIndex.build() + buildDualIndex() → leafCliqueInfo, cliqueLeafIds,
     counting
       coreC[i] = counting[i] for all r-cliques
       vertexProxy[v] = max(coreC[id] for all r-cliques containing v)

     computeHIndex(cliqueId):
       buckets.clear()
       for each leafId in cliqueLeafIds[cliqueId]:
         leaf = tree.adj_list[leafId]
         if leaf.empty(): continue
         // Classify leaf vertices into: inC (members of this r-clique) vs
     others
         // Others split into otherKeeps / otherPivots (relative to leaf's
     pivot/keep)
         cPivots = count of C's vertices that are pivots in this leaf
         effectiveNeedPivot = (s - keepC) - cPivots
         if effectiveNeedPivot < 0 or > |otherPivots|: continue

         minOtherKeepProxy = min(vertexProxy[v] for v in otherKeeps)
         if effectiveNeedPivot == 0:
           bucket[floor(minOtherKeepProxy)] += 1
         else:
           sort otherPivots by vertexProxy descending
           generate breakpoints (same trick as r=1 computeHIndex)

       return bucket_scan(buckets)

     Iteration:
       Phase 1: full scan of all r-cliques, compute H-index, update coreC
       Phase 2: dirty-queue — when coreC[C] decreases, update vertexProxy for
     C's vertices,
                enqueue co-leaf r-cliques via leafCliqueInfo
       Converge when queue empty

     Per-evaluation cost: O(leaves_per_clique × leaf_size) — same order as r=1.

     Risk: vertexProxy is an approximation. May converge to different values
     than peeling.

     Variant B: Exact leafCliqueInfo Local H-Index

     File: NucleusCoreDecompositionRCliqueLocalCPI_Exact.cpp

     Core idea: For each r-clique C in leaf L, iterate ALL other r-cliques D in
     leafCliqueInfo[leafId]. Check if C and D can co-exist in an s-clique (i.e.,
      C's vertices ∪ D's vertices are all in the leaf and the combined pivots
     don't exceed needPivot). Group valid neighbors by min(coreC[D]) into
     buckets. H-index from bucket scan.

     Algorithm:
     Init: same as Variant A (cliqueIndex + dual index + counting)
       coreC[i] = counting[i]

     computeHIndex(cliqueId):
       cliqueSpan = cliqueIndex.byId(cliqueId)
       buckets.clear()

       for each leafId in cliqueLeafIds[cliqueId]:
         leaf = tree.adj_list[leafId]
         if leaf.empty(): continue
         keepC/pivotC = count keeps/pivots in leaf
         needPivot = s - keepC

         // Count pivots in C within this leaf
         cPivots = 0
         for v in cliqueSpan:
           pos = mapRef[v]  // position in leaf
           if leaf[pos].isPivot: cPivots++

         // For each OTHER r-clique D in this leaf:
         for entry in leafCliqueInfo[leafId]:
           if entry.cliqueId == cliqueId: continue
           dSpan = cliqueIndex.byId(entry.cliqueId)

           // Check: can C and D co-exist in an s-clique from this leaf?
           // They can iff: all vertices of C ∪ D are in the leaf (guaranteed by

           // AND the combined pivot count of (C ∪ D) ≤ needPivot
           // (because an s-clique needs exactly needPivot pivots from the leaf)
           unionPivots = count unique pivots in C ∪ D within this leaf
           if unionPivots > needPivot: continue  // can't both fit in any
     s-clique

           // They CAN share s-cliques. Contribution to H-index:
           // Number of s-cliques containing BOTH C and D =
     nCr[remainingPivots][remainingNeed]
           // where remainingPivots = pivotC - unionPivots, remainingNeed =

           remaining = pivotC - unionPivots

  Analysis

  Variant B (Exact CPI) is correct but much slower than V4 peeling. The root
  cause: each H-index re-evaluation requires enumerating C(otherPivots, 
  effectiveNeedPivot) s-clique subsets AND C(s, r) r-subcliques per s-clique —
  this is the same bottleneck as the existing RCliqueLocal, just with
  cliqueLeafIds instead of intersect_dense_sets_multi for leaf lookup.

  Key numbers on com-youtube:
  - 11.7M r-clique re-evaluations across 27 iterations
  - Each re-evaluation does expensive per-leaf enumeration
  - V4 peeling only does 444 iterations with 1.7M BK calls total

  Variant A (Vertex-Proxy) is fast (2589ms on email-Eu-core, faster than V4's 
  190ms... wait, that's slower) but produces incorrect results. The vertex proxy
   vertexProxy[v] = max(coreC[id]) is too coarse — it over-estimates neighbor
  cores, causing the H-index to converge to values higher than the true peeling
  cores.

  Conclusion

  The Local H-index framework eliminates BK and tree mutation but does not 
  eliminate the fundamental enumeration cost. For r≥3, computing the exact
  H-index inherently requires knowing which r-cliques share s-cliques — and
  enumerating these relationships is expensive regardless of whether you do it
  during peeling (BK) or during H-index evaluation (combinatorial enumeration).

  V4 peeling remains the fastest correct approach because:
  1. Its "leaf-death fast path" handles 680K/1.7M cases without BK
  2. BK only fires on the ~40% of cases that truly need re-splitting
  3. The leafCliqueInfo index avoids re-enumeration in the support update phase

  The new CPI Local Exact variant is a correct alternative algorithm that may be
   useful for parallelization (each r-clique is independent), but for
  single-thread performance, V4 wins by 20x.

  Why the CPI Local approach is slower

  The fundamental insight we validated: it's not BK or tree mutation that's the 
  bottleneck — it's the inherent cost of determining which r-cliques share 
  s-cliques.

  - V4 peeling handles 40% of cases via "leaf-death" (O(1) per leaf, no
  enumeration), and only pays BK cost on the remaining 60%
  - Local H-index pays the full enumeration cost on every re-evaluation — 11.7M
  evaluations on com-youtube, each doing C(otherPivots, needPivot) × C(s,r) work
   per leaf
  - The vertex-proxy (Variant A) avoids this enumeration cost entirely
  (O(leaf_size) per eval like r=1) but the approximation is too loose —
  converges to wrong values

  What we learned

  1. SDCT + peeling is not the bottleneck — the BK re-splitting is a relatively
  efficient way to handle the r-clique removal problem compared to full
  re-enumeration
  2. The r=1 breakpoint trick doesn't generalize exactly to r≥3 — the
  vertex-proxy core doesn't capture the combinatorial structure of r-clique
  neighborhoods in s-cliques
  3. V4 remains the best single-thread r≥3 variant at 2.28x speedup over
  baseline
  4. The Local CPI Exact variant is a valid alternative algorithm useful for
  future parallelization work (each r-clique evaluation is independent), but not
   competitive in single-thread performance
